# 版付きルールと内部Agentの署名付きIntent

> この文書は開発段階ごとの計画・判断を整理したものです。状態と検証結果はその範囲に限ります。後続の変更と現行仕様は[ロードマップ](../roadmap.md)を参照してください。

## Context

チャットによる設定と、その設定に従う自動実行を別々に追跡する必要がある。外部Agentや本番認証は初期では未選択。

## Decision

銀行提供の内部Agentを初期実装に採用する。同一Node内で別モジュールにし、Agent署名鍵と銀行資産鍵は別に持つ。チャットはrule draftを作り、具体条件への利用者の肯定応答を提案ID・版へ紐付けて構造化ルールを保存・有効化する。別ボタンは必須にしない。サンプルメールの閲覧許可後、読取り・抽出を完了して結果と根拠を示してから条件を提案し、送金は具体条件が揃った有効ルールに基づいて実行する。初期は支払い/運用各1有効ルールとする。

IntentはEIP-712署名し、顧客・ルール版・根拠・操作種別・実金額・相手先/運用先・期限・nonce・デモinstanceを束縛する。銀行が署名、所有関係、現在のルール版、残高、金額を再検証する。変更・停止済みの版のIntentは実行しない。API利用者が任意のcalldataやasset addressを指定できる入口を設けない。

## Alternatives

会話履歴を都度解釈すると有効設定が曖昧になる。署名無し内部関数は単純だがAgentのIntent提出・署名検証を示せない。外部Agentプロセスは認証・運用範囲が増える。

## Consequences

設定の根拠と実行内容を追跡できる。署名検証はbackendであり、コントラクトがAgent署名や全Policyを検証する設計ではない。同一プロセスのためOSレベルの秘密分離はない。

## 実装時の具体条件

支払いルールはmaxPaymentJpyに加えてmonthlyLimitJpyを持つ。月合計はAsia/Tokyoのデモ時計における実行月・顧客・受取先単位で集計し、ルールの変更・再作成ではリセットしない。期日の到来した未払い請求を期日・invoiceKey順に処理し、各送信直前に確定支払額＋送信予約額＋今回額を照合する。予約は確定後に実績へ置き換え、重複加算しない。開始前のfixture履歴も当月分なら算入する。

支払いルールは受取先ごとの1件上限・月次上限を保持できる。各請求書は一致する受取先の個別上限に照合し、月次使用額も受取先ごとに集計する。承認済みルールに含まれる受取先の請求書だけを送金予定に表示・実行する。初期サンプルではアオバデザイン20万円/月、サクラオフィス10万円/月を別々に提案し、チャットで両方の条件を提示してから一括同意を得る。

payment/investmentはruleId/versionを許可根拠にし、redemptionは利用者のmessageId・lockId・元顧客・残元本を根拠にする判別unionとする。償還に運用ルールの有効状態を要求しない。共通の署名・所有権検証は維持する。メール閲覧grantとproposal（根拠・条件・baseVersion・同意messageId）は別テーブルで保存する。

変更と同意のtransactionはrule version更新・proposal確定・同意記録を一括処理する。APIからの直接変更も同じサービスに通す。償還APIはチャット依頼と所有者の対応を検証し、メール本文や任意のmessageIdを同意の代替にしない。

## 後続判断

[API権限分離](0011-human-agent-api-authorization.md)により、チャットの肯定応答は承認画面を開始する契機となる。即時acceptや任意messageIdによる償還許可は現行方式では使わず、本人に束縛したchallenge・一回限りの償還requestを用いる。
