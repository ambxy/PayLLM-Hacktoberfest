# 口座作成時の顧客専用publicウォレット生成

> この文書は開発段階ごとの計画・判断を整理したものです。状態と検証結果はその範囲に限ります。後続の変更と現行仕様は[ロードマップ](../roadmap.md)を参照してください。

## Context

銀行在庫と顧客運用資産を区別し、再起動やデモresetで鍵を失わない構成を定める。

## Decision

銀行口座作成と同時に専用Ethereum鍵を生成し、口座ID・chainId・アドレスを保存する。既存口座の再初期化は既存ウォレットを再利用し、同じ作成要求を再送しても増殖しない。銀行在庫は別ウォレット。銀行が両方を管理し、Agentは別鍵でIntentだけを署名する。public取引は銀行側Policy検証後、サーバーで署名する。Anvil既知鍵をpublic署名へ流用しない。

Node標準cryptoのAES-256-GCM、暗号学的乱数で生成する鍵、毎回異なる12-byte nonceと認証タグを使う。32-byte master keyはサーバー環境のみに置き、DB/Git/ログ/ブラウザに保存しない。暗号文・keyVersion・nonce・tagは専用walletレコードへ、AADは口座ID・chainId・アドレス・keyVersionへ結び付ける。復号後も導出アドレスを照合する。master key欠落時に平文保存や自動再生成へ退避しない。ファイルによる環境設定はGit対象外・所有者のみ読書きとする。

ウォレット情報はdemo instanceから独立して永続化し、instance削除にcascadeしない。新規口座作成はDBトランザクションとunique制約で口座と暗号化鍵を一緒に確定する。既存固定デモユーザーには明示的な初回移行を適用する。公開APIが返すのはアドレスと準備状態のみ。銀行在庫鍵は運用者が同じ暗号化ストアへローカルCLIで取り込み、入力をログやシェル履歴に残さない。

## Alternatives

ブラウザ署名を毎回求める方式はAgentによる自動運用の体験に合わない。KMS/HSMは本番化時に再検討し、ローカルデモにクラウド契約を必須にしない。

## Consequences

ウォレット作成時にpublic送信は不要。署名にはSepolia ETHが必要。暗号文DBとmaster key両方の保持が必要で、鍵紛失の自動復旧は対象外。ローカル暗号化保管は本番用の鍵管理基盤を実証するものではない。

## 鍵の生成と取り込み

環境変数から既存鍵を取り込む方式は、同じ環境の再現に使える一方、複数環境で共有するとnonce・残高・持分が競合する。公開テンプレートの鍵欄は空とし、利用者が環境ごとに生成または設定する。master keyも環境固有とする。既存DBと異なる鍵を指定した場合は上書きせず拒否する。
